# Supermemory

Долговременная память DeepSeek Harness на официальном Supermemory API v5. Плагин использует тот же сервер, что и
официальный плагин Supermemory для Гермеса, поэтому история Гермеса доступна без миграции: у DeepSeek Harness
собственный namespace для записи, а namespace Гермеса читаются только на чтение и всегда помечаются как чужой опыт.

## Разделение памяти

| Namespace | Кто пишет | Как используется |
|---|---|---|
| `dsh` | DeepSeek Harness | Свои сохранённые факты, профиль и документы сессий. |
| `hermes_default` | Гермес, профиль по умолчанию | Только чтение, **если** добавлен в `readContainers`. |
| `hermes`, `hermes_*` | Гермес, другие контейнеры и профили | Только чтение, если включены `readPrefixes`. |

Чужое чтение по умолчанию выключено (`readContainers: []`, `readPrefixes: []`): свежая установка
трогает только свой namespace, а память другого агента подключается явным оверрайдом.

Гермес — другой агент. Его факты в recall попадают в отдельную секцию с подписью «Agent Hermes — another agent»,
а системная инструкция запрещает выдавать их за действия DeepSeek Harness и писать в его namespace.

## Что происходит автоматически

1. **Перед ходом.** Последний вопрос пользователя ищется в своём namespace и в читаемых (до трёх) в режиме
   `recallSearchMode` (по умолчанию `memories` — извлечённые памяти, без дублей чанков) с порогом `recallThreshold`
   (0.5) и лимитом `recallMaxResults` (5); запрос короче `minQueryChars` (12) и запросы с `/`, `!`, `#` не ищутся,
   длиннее `recallQueryMaxChars` — обрезаются. Найденные факты входят в шаг сообщением `<<<supermemory-<nonce>>>>`:
   заголовок с предупреждением, затем факты по контейнерам с процентом релевантности, датой, пометками
   `superseded`/`inferred`/`forgotten`, id memory (не документа) и — при `recallIncludeRelated` — одной строкой
   связи (`↳ updates v1 (earlier, 2026-10-01): …`); каждый факт обрезается до `recallFactMaxChars`.
   Уже показанные в сессии факты пропускаются (`recallDedupe`, счётчик `N new · M already in context`), набор
   сбрасывается на компакции. Профиль обновляется на первом ходу и далее каждые `profileFrequency` ходов, причём
   параллельно с поиском и отдельными секциями (`Known profile facts`, `Recent context`, buckets, `+N more`),
   а на промежуточных ходах не подмешивается из кеша. Бюджет профиля общий и не больше половины блока.
   Если recall не успел или упал, в блоке появляется строка `memory recall unavailable (<причина>) — proceed without
   memory` (`recallFailureNotice`), причина — класс (`timeout`/`unreachable`/`not configured`/`error`), а не текст
   сервера; неудачный capture тоже виден в следующем блоке (`captureFailureNotice`). Если память ничего не нашла,
   один раз за сессию приходит подсказка, что вызвать инструмент поиска (`discoveryNotice`). Успешный одинаковый
   поиск переиспользуется между сессиями (`recallQueryCacheMs`), но не внутри одной. В конце блока — правило
   атрибуции: recalled-текст это данные, а не инструкции, и факт из Supermemory так и называется.
2. **После хода.** Завершённая сессия перезаписывается как один документ `dsh-<sessionId>`; если не влезает в
   `maxCaptureChars` — по частям `…-p1…pN`, которые обновляются на месте. Хеш считается по содержимому без
   изменчивых полей, поэтому неизменившийся ход не перезаписывает документы и не запускает обработку заново.

   Каждый документ получает `date` — время начала сессии для одного документа и самого раннего хода для части
   (по времени событий `session/event`, а не по времени записи; для сессии, начатой до загрузки плагина, это первое
   наблюдённое событие; для части без наблюдённых времён поле не отправляется),
   `group` `{project, kind, project_id}` и metadata `project`/`kind`/`project_id`: `project_id` — 16 hex-символов
   от нормализованного git-remote (или хеша реального пути), поэтому клоны одного репозитория совпадают, а сырой путь
   на сервер не уходит. `taskType: "memory"` и `dreaming` (`captureDreaming`, по умолчанию `dynamic` — связанные
   захваты обрабатываются вместе; `instant` доступен) передаются и в `POST`, и в `PATCH`.

   В транскрипт входят вызовы инструментов и их результаты (`captureTools`, до `captureToolChars` на результат,
   с именем и пометкой ошибки; свои `supermemory_*` исключены), поэтому команды, падения и правки файлов тоже
   попадают в память. `<private>…</private>` вырезается, а полностью приватный ход отбрасывается вместе с ответом;
   base64 data URI заменяются на `[image]`, секреты дополнительно вычищаются (URL-креды, JWT, `KEY=value`), а
   `captureContext` (по умолчанию — guidance про долговременные факты) направляет извлечение на сервере.

   Компакция в DSH не дописывает текст: она добавляет `user/message` с `source.kind = 'compact-checkpoint'`,
   который заменяет на поверхности все предыдущие сообщения. Такой чекпоинт сохраняется в транскрипте как
   «Summary of earlier turns (compacted)» и **переключает семейство документов** (`…-c<hash>`): прежние части
   остаются нетронутыми, потому что в текущей поверхности этих ходов уже нет. Удаляются только документы того же
   семейства, которые текущий план больше не покрывает.
3. **В промпте.** Постоянная секция «Supermemory» объясняет модель, где её память, что Гермес — другой агент и что
   recall — это фон, а не инструкции.

## Временная правда и эволюция

API v5 хранит не плоский набор фактов, а граф: у памяти есть `isLatest`, `version`,
`isInference`, `isForgotten`, `system.createdAt/updatedAt`, а `include.related` отдаёт
`parents`/`children`/`siblings` со связями `updates` (заменяет), `extends` (дополняет),
`derives` (выведено). `GET /ns/{ns}/memories/{id}` возвращает версии «до трёх шагов»,
связи и исходный документ. Плагин пробрасывает это так:

- `supermemory_search` с `includeRelated`/`includeForgotten`/`includeDocuments` рендерит даты,
  состояние и до трёх связей на факт;
- `supermemory_memory_history` читает одну память: цепочку версий, `extends`/`derives`, дату и
  (по флагу) фрагмент исходного документа;
- recall может показывать по одной связи на факт (`recallIncludeRelated`), не выходя из бюджета.

Полная матрица «путь/параметр API → инструмент или осознанный отказ → тест» —
[docs/API-COVERAGE.md](API-COVERAGE.md).

## Skill

Бандл регистрирует skill `supermemory` в каталоге skill'ов DSH (`ctx.skills.register`, сервис
необязательный): процедура «когда искать и когда нет», что считать долговременным фактом, как читать
историю одной памяти, как индексировать проект без секретов и транзиентного состояния, как безопасно
забывать, и что recalled-текст — недоверенные данные. Модель загружает его инструментом `skill`, когда
задача зависит от прошлой работы, вместо того чтобы держать всё в системном промпте.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `supermemory_search` | Семантический поиск по всем читаемым namespace или по указанному; `filter`, `threshold`, `rerank`, `rewriteQuery`, `includeRelated`/`includeForgotten`/`includeDocuments`. |
| `supermemory_memory_history` | Одна память по id: текст, цепочка версий, `extends`/`derives`, даты, состояние, фрагмент документа. Только чтение. |
| `supermemory_profile` | Постоянные факты и свежий контекст, опционально с запросом, `filter` или выбранными `buckets`. |
| `supermemory_save` | Сохранить документ в записываемый namespace с `date`/`group`/`dreaming` (обработка асинхронная). |
| `supermemory_save_many` | Сохранить 1–50 сфокусированных документов одним batch-вызовом (с вычисткой секретов). |
| `supermemory_forget` | Удалить память по id или по описанию; удаление по описанию сначала показывает совпадения, удаление — только с `confirm: "delete"`. Параметра `dryRun` у инструмента нет. |
| `supermemory_read_document` | Прочитать сохранённый документ или прошлую беседу по id, с постраничным смещением (текст — недоверенные данные). |
| `supermemory_list` | Документы, чанки или memories: страницы, `sort`/`order`, `filter`, forgotten. |
| `supermemory_namespaces` | Подключение, собственный namespace и все namespace сервера со счётчиками и страницами. |
| `supermemory_upload_file` | Файл (PDF, картинка, офисный документ) в память; только внутри `uploadRoots`. |
| `supermemory_namespace` | Список, `show` (текущий `supportingContext`), установка контекста, удаление (allowlist + `confirm: delete`). Создать namespace нельзя. |
| `supermemory_buckets` | Профильные buckets: список, задать, удалить. |

## Настройка

Ключ API хранится в credential-ссылке `SUPERMEMORY_API_KEY` (`$DSH_HOME/.credentials.yaml`). Адрес сервера и
контейнеры задаются в строке плагина в `cordis.patch.yml`:

```yaml
- id: supermemory
  name: '@local/dsh-supermemory'
  config:
    baseUrl: http://localhost:6767
    container: dsh
    readContainers: [hermes_default]
    readPrefixes: [hermes]
```

Полный список полей — в README пакета. По умолчанию `baseUrl` — `http://127.0.0.1:6767` (порт локального сервера
`npx supermemory local` в текущих релизах; в старых было 8787). Сервер Гермеса на этой машине тоже слушает 6767,
поэтому совпадает; если он на другом порту — переопределите `baseUrl`.

## Защита

- Recall-блок и блок документа (`supermemory_read_document`) ограничены одноразовым nonce; из
  недоверенного текста убираются управляющие символы (включая одиночный `\r`, который Markdown тоже
  считает переводом строки), устаревший тег `<supermemory-context>`, поддельные `<<<supermemory-…>>>`
  и заголовки `##`. Проверка заголовков линейна по входу.
- Тело ошибки сервера не передаётся вовсе: ошибка называет endpoint, HTTP-статус и (если это
  идентификатор, не содержащий ключ) машинный код, плюс фиксированную подсказку для типового статуса.
  Отказы удаления рендерятся только как id и безопасные коды: строковая запись без формы
  идентификатора превращается в «unidentified entry». Поэтому endpoint, который эхом вернёт ключ или
  напишет инструкции, не попадёт ими в контекст модели.
- Capture удаляет только те документы, которые сам написал: перед удалением legacy-документа
  сессии он перечитывается и проверяются `session_id` и метаданные агента.
- Валидация фильтров и групп отвергает неверную форму до запроса и не эхоит отвергнутые значения.
- Состояние capture вытесняет только простаивающие сессии (с таймером или выполняющимся flush они
  остаются), а таймеры сбрасывают свой handle при срабатывании.

## Ограничения

- Новые документы становятся memories и попадают в профиль не сразу: обработка на сервере асинхронная.
  Памяти и версии появляются на второй фазе («dreaming»): `instant` — сразу после обработки и за одну
  дополнительную операцию на документ, `dynamic` — группами, может занимать минуты. Для этой фазы
  self-hosted серверу нужна рабочая модель извлечения; без неё документ сохраняется и ищется как чанк,
  но новых memories не появляется.
- При недоступном сервере инструменты возвращают понятную ошибку, а ход продолжается без recall.
- Recall добавляет один поисковый запрос к первому шагу хода и ограничен бюджетом `recallTimeoutMs` (по умолчанию
  10 с); при таймауте ход не блокируется.
- Обычный API-запрос ждёт до `timeoutMs` (по умолчанию 120 с, потолок 300 с): занятый локальный сервер отвечает
  дольше, и лучше дождаться ответа, чем потерять результат и показать ошибку. Мёртвый сервер по-прежнему
  отказывает сразу — `ECONNREFUSED` не таймаут.
- Субагенты по умолчанию не читают и не пишут память, чтобы не засорять её своими транскриптами.
- Запись в namespace Гермеса запрещена всегда: `allowWritesToReadContainers` на `hermes*` не распространяется.
- Плагин не переносит данные между namespace. Серверное состояние он меняет только явными инструментами:
  `supermemory_namespace` задаёт `supportingContext` и удаляет namespace, `supermemory_buckets` задаёт и удаляет
  buckets; документы читаются и пишутся через официальный API.

## Почему не официальный MCP-сервер

У Supermemory есть официальный MCP-сервер (`https://mcp.supermemory.ai/mcp`, OAuth). Он даёт модели инструменты, но не
даёт автоматического recall перед ходом, capture сессии и разделения «свой namespace / чужие только на чтение» — это
пришлось бы настраивать отдельно, а локальный сервер он не покрывает. Этот плагин использует тот же официальный API
v5 напрямую (как официальный Hermes-плагин), поэтому работает и с локальным сервером, и с облаком.

## Фильтры и статус обработки

В метаданные документа плагин пишет `sm_source`, `source_agent`, `type`
(`conversation` / `note`), `session_id`, `turns`, `workspace`, `updated_at`.
Фильтр по этим ключам передаётся в `/search` как `filter` и сужает выдачу до
нужного типа документов; из конфига он применяется только к своему namespace,
чтобы не отбрасывать факты чужих агентов с другой схемой метаданных.

Обработка документа асинхронная: запись отвечает сразу, а `system.status`
проходит `queued` → `processing` → `done`. `supermemory_save` ждёт результат в
пределах `ingestWaitMs` и сообщает фактический статус, а не обещание.

## Длинные сессии, файлы, namespace и buckets

Сессия, которая влезает в `maxCaptureChars`, остаётся одним документом `dsh-<sessionId>`; которая не влезает —
режется по границам ходов на `dsh-<sessionId>-p1…pN` (по `captureTurnsPerChunk` ходов), и при переходе через
лимит одиночный документ удаляется, чтобы факты не дублировались. Если поверхность сессии уменьшилась
(rewind/rewrite), старые части не удаляются; компакция переключает семейство документов и также не трогает прежние
части.

`supermemory_upload_file` использует `/document/file` и читает локальный диск, поэтому выключен по умолчанию и
ограничен `uploadRoots`: путь канонизируется, файл вне разрешённых каталогов отвергается.

`supermemory_namespace` умеет список, `supportingContext` и удаление (`confirm: delete`, отказ для своего и
гермесовых namespace). Сервер не умеет создавать namespace — `POST /ns` в API отсутствует. `supermemory_buckets`
управляет профильными buckets (`/profile/buckets`).

## Проверка после установки

Инструменты появляются в сессии как `supermemory_search`, `supermemory_profile`, `supermemory_save`,
`supermemory_forget`, `supermemory_read_document`, `supermemory_list`, `supermemory_namespaces`. Быстрый тест:
`supermemory_namespaces` (подключение и счётчики), затем `supermemory_search` с запросом о Гермесе — результаты должны
быть помечены контейнером `hermes_default`.

Проверено на живом сервере 25.11.2026: все десять инструментов зарегистрированы, поиск возвращает факты из
`hermes_default` (11 682 memories), запись в `dsh` создаёт документ и через обработку даёт memories и профиль,
дочерний агент с включённым recall ответил фактом из памяти Гермеса, а завершённая сессия была записана одним
документом `dsh-<sessionId>`.
