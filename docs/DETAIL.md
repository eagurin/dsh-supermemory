# Supermemory

Долговременная память DeepSeek Harness на официальном Supermemory API v5. Плагин использует тот же сервер, что и
официальный плагин Supermemory для Гермеса, поэтому история Гермеса доступна без миграции: у DeepSeek Harness
собственный namespace для записи, а namespace Гермеса читаются только на чтение и всегда помечаются как чужой опыт.

## Разделение памяти

| Namespace | Кто пишет | Как используется |
|---|---|---|
| `dsh` | DeepSeek Harness | Свои сохранённые факты, профиль и документы сессий. |
| `hermes_default` | Гермес, профиль по умолчанию | Только чтение: recall и инструменты. |
| `hermes`, `hermes_*` | Гермес, другие контейнеры и профили | Только чтение, подхватываются по префиксу `hermes`. |

Гермес — другой агент. Его факты в recall попадают в отдельную секцию с подписью «Agent Hermes — another agent»,
а системная инструкция запрещает выдавать их за действия DeepSeek Harness и писать в его namespace.

## Что происходит автоматически

1. **Перед ходом.** Последний вопрос пользователя ищется в своём и читаемых namespace. Найденные факты входят в шаг
   сообщением `<supermemory-context>`: заголовок с предупреждением, затем факты по контейнерам с процентом
   релевантности и id документа. Профиль подмешивается на первом ходу и далее каждые `profileFrequency` ходов.
2. **После хода.** Завершённая сессия целиком перезаписывается как один документ `dsh-<sessionId>`: пользовательские
   и ответные сообщения, без служебных сообщений и без самого блока recall. Повторная запись обновляет тот же
   документ, поэтому правки и compaction не плодят копии. Supermemory обрабатывает документ асинхронно.
3. **В промпте.** Постоянная секция «Supermemory» объясняет модель, где её память, что Гермес — другой агент и что
   recall — это фон, а не инструкции.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `supermemory_search` | Семантический поиск по всем читаемым namespace или по указанному. |
| `supermemory_profile` | Постоянные факты и свежий контекст, опционально с поиском по запросу. |
| `supermemory_save` | Сохранить документ в записываемый namespace (обработка асинхронная). |
| `supermemory_forget` | Удалить память по id или по описанию (с предварительным просмотром `dryRun`). |
| `supermemory_read_document` | Прочитать сохранённый документ или прошлую беседу по id, с постраничным смещением. |
| `supermemory_list` | Список документов или memories в namespace. |
| `supermemory_namespaces` | Подключение, собственный namespace и все namespace сервера со счётчиками. |

## Настройка

Ключ API хранится в credential-ссылке `SUPERMEMORY_API_KEY` (`$DSH_HOME/.credentials.yaml`). Адрес сервера и
контейнеры задаются в строке плагина в `cordis.patch.yml`:

```yaml
- id: supermemory
  name: '@local/dsh-supermemory'
  config:
    baseUrl: http://localhost:6767
    container: dsh
    readContainers: [hermes_default]
    readPrefixes: [hermes]
```

Полный список полей — в README пакета. Значения по умолчанию рассчитаны на локальный сервер `npx supermemory local`
на порту 6767, тот же, что использует Гермес.

## Ограничения

- Новые документы становятся memories и попадают в профиль не сразу: обработка на сервере асинхронная.
- При недоступном сервере инструменты возвращают понятную ошибку, а ход продолжается без recall.
- Recall добавляет один поисковый запрос к первому шагу хода и ограничен бюджетом `recallTimeoutMs` (по умолчанию
  2,5 с); при таймауте ход не блокируется.
- Субагенты по умолчанию не читают и не пишут память, чтобы не засорять её своими транскриптами.
- Запись в namespace Гермеса запрещена, пока явно не включён `allowWritesToReadContainers`.
- Плагин не переносит данные и не меняет настройки namespace на сервере: он только читает и пишет документы через
  официальный API.

## Почему не официальный MCP-сервер

У Supermemory есть официальный MCP-сервер (`https://mcp.supermemory.ai/mcp`, OAuth). Он даёт модели инструменты, но не
даёт автоматического recall перед ходом, capture сессии и разделения «свой namespace / чужие только на чтение» — это
пришлось бы настраивать отдельно, а локальный сервер он не покрывает. Этот плагин использует тот же официальный API
v5 напрямую (как официальный Hermes-плагин), поэтому работает и с локальным сервером, и с облаком.

## Фильтры и статус обработки

В метаданные документа плагин пишет `sm_source`, `source_agent`, `type`
(`conversation` / `note`), `session_id`, `turns`, `workspace`, `updated_at`.
Фильтр по этим ключам передаётся в `/search` как `filter` и сужает выдачу до
нужного типа документов; из конфига он применяется только к своему namespace,
чтобы не отбрасывать факты чужих агентов с другой схемой метаданных.

Обработка документа асинхронная: запись отвечает сразу, а `system.status`
проходит `queued` → `processing` → `done`. `supermemory_save` ждёт результат в
пределах `ingestWaitMs` и сообщает фактический статус, а не обещание.

## Длинные сессии, файлы, namespace и buckets

Сессия, которая влезает в `maxCaptureChars`, остаётся одним документом `dsh-<sessionId>`; которая не влезает —
режется по границам ходов на `dsh-<sessionId>-p1…pN` (по `captureTurnsPerChunk` ходов), и при переходе через
лимит одиночный документ удаляется, чтобы факты не дублировались. Обратный переход (компакция уменьшила сессию)
удаляет лишние части.

`supermemory_upload_file` использует `/document/file` и читает локальный диск, поэтому выключен по умолчанию и
ограничен `uploadRoots`: путь канонизируется, файл вне разрешённых каталогов отвергается.

`supermemory_namespace` умеет список, `supportingContext` и удаление (`confirm: delete`, отказ для своего и
гермесовых namespace). Сервер не умеет создавать namespace — `POST /ns` в API отсутствует. `supermemory_buckets`
управляет профильными buckets (`/profile/buckets`).

## Проверка после установки

Инструменты появляются в сессии как `supermemory_search`, `supermemory_profile`, `supermemory_save`,
`supermemory_forget`, `supermemory_read_document`, `supermemory_list`, `supermemory_namespaces`. Быстрый тест:
`supermemory_namespaces` (подключение и счётчики), затем `supermemory_search` с запросом о Гермесе — результаты должны
быть помечены контейнером `hermes_default`.

Проверено на живом сервере 25.11.2026: все семь инструментов зарегистрированы, поиск возвращает факты из
`hermes_default` (11 682 memories), запись в `dsh` создаёт документ и через обработку даёт memories и профиль,
дочерний агент с включённым recall ответил фактом из памяти Гермеса, а завершённая сессия была записана одним
документом `dsh-<sessionId>`.
